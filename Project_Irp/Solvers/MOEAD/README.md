# MOEAD — MOEA/D solver for the many-objective IRP

Decomposition-based many-objective evolutionary algorithm (via
[pymoo](https://pymoo.org)'s own `MOEAD`), applied to the same Inventory
Routing Problem (IRP) as `Solvers/NSGA3/` and `Solvers/QINSGA3/`. Reuses
pymoo's `MOEAD` structure unchanged except for two small, targeted
subclasses (below) that close two gaps found while integrating it into
this project — neither gap is specific to the IRP, both would affect any
constrained, heterogeneous-scale problem run through pymoo's stock
`MOEAD`.

## Concept

NSGA-III and QI-NSGA-III both search the whole objective space at once and
use reference directions only to *steer diversity* during environmental
selection (niching). MOEA/D takes a different starting point: it
**decomposes** the many-objective problem into `N` (= number of reference
directions) single-objective **scalar subproblems**, one per direction,
solved *simultaneously* and *cooperatively*:

```
g^ws(x | z, z*) = max_j  w_j · |f_j(x) − z*_j|          (weighted Tchebycheff)
```

where `z*` is the running ideal point (component-wise best objective value
seen so far) and `w = (w_1,…,w_M)` is subproblem `i`'s own reference
direction, reused directly from `w = z^i` — this project's MOEA/D uses the
*same* Das-Dennis reference-direction set NSGA-III/QI-NSGA-III already use
for their own niching, just repurposed here as **decomposition weight
vectors** instead. Each subproblem `i` keeps exactly one individual `x_i`;
minimizing `g^ws(x | w^i, z*)` for every `i` simultaneously traces out an
approximation of the whole Pareto front, one point per direction. There is
no separate "environmental selection" step at all — a subproblem's
individual is simply replaced by a better-scoring offspring, evaluated
directly against its own and its *neighbours'* scalarized values (below).

**Neighbourhoods.** Subproblems whose weight vectors are close together
(Euclidean distance between `w^i` and `w^k`) represent similar trade-offs,
so their optimal solutions tend to be similar too. MOEA/D exploits this:
subproblem `i`'s `T` nearest neighbours (`n_neighbors=20`, pymoo's own
default, not tuned here) supply its mating parents *and* are the only
subproblems an offspring bred from `i` is allowed to replace into. This is
what makes MOEA/D's search cooperative rather than a set of `N` independent
single-objective runs: good genetic material spreads locally along the
weight-vector simplex, generation by generation.

## Algorithm

Per generation, for **every** subproblem `i = 1..N` (`N = len(ref_dirs)`,
165 for this project's 4 objectives — see
[Parameters](#parameters-and-references) for why this can't be 200 like
the other two solvers):

1. **Select mating parents** from subproblem `i`'s neighbourhood `B(i)`
   (with probability `prob_neighbor_mating=0.9`, pymoo's own default) or,
   the remaining 10% of the time, from the whole population — the small
   escape hatch that keeps genetic diversity from collapsing to purely
   local exchange along the simplex.
2. **Vary** — SBX crossover + polynomial mutation (PM) produce one
   offspring `y`, the *same* operators (same `eta`, same probability
   conventions) `Solvers/NSGA3/` and `Solvers/QINSGA3/` use, for a fair
   operator-level comparison across all three solvers.
3. **Evaluate** `y`: objectives `F(y)` and constraint violation `CV(y)`
   (`IRPProblem._evaluate`, unmodified, shared by all three solvers).
4. **Update the ideal point** `z*` component-wise from every objective
   value seen so far (pymoo's own `self.ideal`, tracked automatically).
5. **Update the running nadir estimate** — this project's own addition,
   see [below](#why-pymoos-stock-moead-needed-two-subclasses) — from the
   union of `y`'s objectives and every neighbour's.
6. **Replace** — for each neighbour `k ∈ B(i)`: compare `x_k` and `y` using
   Deb (2000)'s feasibility rule (feasible beats infeasible; between two
   feasible or two infeasible individuals, decide by the normalized
   weighted-Tchebycheff value / by constraint violation respectively — see
   [below](#why-pymoos-stock-moead-needed-two-subclasses)) and overwrite
   `x_k` with `y` if `y` wins.

Repeat for `n_gen` generations; the final population (one individual per
subproblem) — filtered to its own non-dominated subset — is the returned
Pareto set.

## Pseudocode

Zhang & Li (2007)'s original MOEA/D-DE-style replacement loop, exactly as
pymoo's `MOEAD` implements the outer structure, with this project's two
subclasses' logic inlined where they diverge from pymoo's stock behaviour
(marked `# ★ project addition`):

```
Input : reference directions / weight vectors Z = {w¹,…,w^N}   (Das-Dennis, shared with
                                                                  NSGA-III/QI-NSGA-III)
        neighbourhood size T = 20                                (pymoo default)
        prob_neighbor_mating = 0.9                                (pymoo default)
        generation budget max_gen

N ← |Z|                                    # population size FORCED to |Z| — not independently
                                            #   settable, unlike NSGA-III/QI-NSGA-III's pop_size
B(i) ← T nearest weight vectors to wⁱ, for each i = 1..N     # Euclidean distance, includes i itself
{x_1,…,x_N} ← RandomInit(N)                # FloatRandomSampling
Evaluate(x_1,…,x_N)                        # F(x_i), CV(x_i) — IRPProblem._evaluate
z* ← componentwise min of all F(x_i)       # ideal point, self.ideal in pymoo — tracked automatically
nadir_running ← None                       # ★ project addition, see below

for gen = 1 … max_gen:
    for i = 1 … N:                          # every subproblem gets one offspring per generation
        if rand() < prob_neighbor_mating:
            parents ← 2 random members of B(i)
        else:
            parents ← 2 random members of the WHOLE population
        y ← PM_η( SBX_η(parents) )          # same operators/parameters as NSGA-III/QI-NSGA-III
        Evaluate(y)                         # F(y), CV(y)
        z* ← min(z*, F(y))                  # update ideal point

        # ★ project addition — NormalizedTchebycheff.update_nadir(), called ONCE per
        #   subproblem-i replacement step, on the UNION of the neighbourhood's F and F(y),
        #   BEFORE either decomposition value below is computed (never inside the scalarizing
        #   function itself — that would let the two calls below use two different,
        #   inconsistently-informed spans within the same comparison)
        nadir_running ← componentwise max(nadir_running, {F(x_k) : k ∈ B(i)} ∪ {F(y)})
        span ← max(nadir_running − z*, ε)   # ε = 1e-9, avoids division by zero

        for k ∈ B(i):
            # ★ normalized weighted Tchebycheff (replaces pymoo's raw, unnormalized version —
            #   see "Objective normalization" below)
            g(x_k) ← max_j  w^k_j · |(F(x_k)_j − z*_j) / span_j|
            g(y)   ← max_j  w^k_j · |(F(y)_j   − z*_j) / span_j|

            # ★ Deb (2000) feasibility rule (replaces pymoo's raw g(y) < g(x_k) comparison,
            #   which pymoo's stock MOEAD cannot even reach here — see "Why two subclasses" below)
            if CV(y) ≤ 0 and CV(x_k) ≤ 0:            # both feasible
                y_wins ← g(y) < g(x_k)
            elif CV(y) ≤ 0 and CV(x_k) > 0:           # y feasible, x_k infeasible
                y_wins ← True
            elif CV(y) > 0 and CV(x_k) ≤ 0:           # y infeasible, x_k feasible
                y_wins ← False
            else:                                     # both infeasible
                y_wins ← CV(y) < CV(x_k)

            if y_wins:
                x_k ← y

return { x_i : x_i is non-dominated among {x_1,…,x_N} }
```

`repair_final_front` (default on, matching NSGA-III/QI-NSGA-III) is applied
AFTER this whole loop returns, by the caller
(`Solvers/NSGA3/report_builder.py::_evaluate_pareto`, shared by all three
solvers) — 2-opt route repair on the decoded chromosomes, Baldwinian, the
chromosomes themselves untouched.

## Why pymoo's stock MOEA/D needed two subclasses

Both gaps were found — not assumed — while integrating MOEA/D into this
project; see `docs/superpowers/specs/2026-08-19-moead-integration-design.md`
for the full investigation trail (including direct inspection of pymoo
0.6.1.6's own source).

### 1. Constraint handling — `ConstrainedMOEAD`

`IRPProblem` (`Solvers/NSGA3/problem.py`) declares real hard inequality
constraints (`n_ieq_constr = 2·|T| + |clients|·|T| + 2·|T|`: the
`tau_return` time window, per-client delivery-deadline coverage, and a
depot-stock-ceiling safety net) — the same constraints NSGA-III's and
QI-NSGA-III's own feasibility-first selection already consumes via pymoo's
constraint-domination. pymoo's stock `MOEAD._setup()` contains
`assert not problem.has_constraints()` — running it against `IRPProblem`
unmodified crashes immediately at setup, not with a soft warning.

`ConstrainedMOEAD` overrides only `_replace()` (line-for-line identical to
pymoo's own `_setup()` otherwise, minus that one assert) to apply **Deb
(2000)'s feasibility rule** in place of the raw scalarized-value
comparison — see the pseudocode above. This rule is:

- **Parameter-free** — no penalty weight to tune, unlike the alternative
  that was explicitly considered and rejected: adding a constant penalty
  to the objectives before decomposition. That alternative would have
  introduced a hyperparameter with no counterpart on the NSGA-III/
  QI-NSGA-III side of this project, undermining a fair cross-algorithm
  comparison.
- **Consistent in spirit with the other two solvers** — NSGA-III/
  QI-NSGA-III already apply "feasibility first" via pymoo's own
  constraint-dominance relation in their non-dominated sorting; Deb's rule
  is the direct decomposition-based analogue of that same principle.
- **A no-op when nothing is infeasible** — every branch collapses to the
  original `g(y) < g(x_k)` comparison when `CV(x_k) ≤ 0` and `CV(y) ≤ 0`
  for every individual involved, which is always true on the unconstrained
  DTLZ/MaF benchmark suite (`Validation/Benchmarking/algorithms/moead/`
  reuses `ConstrainedMOEAD` for exactly this reason, rather than
  maintaining two parallel MOEA/D wirings).

### 2. Objective normalization — `NormalizedTchebycheff`

The IRP's 4 objectives live on very different raw scales (cost ≈
15 000–25 000 DNT, CO₂ ≈ 800–1 500 kg, time ≈ 70–110 h, working capital ≈
3 500–7 000 DNT). NSGA-III's own environmental selection normalizes by
objective *range* before comparing solutions (`ReferenceDirectionSurvival`
tracks both an ideal point **and** a nadir point, monotonic across
generations); QI-NSGA-III's `_normalise_F` reuses that exact same
ideal/nadir pair. Investigating pymoo's `MOEAD._replace()` directly found
no equivalent: it passes only `ideal_point` to the decomposition, never
`nadir_point`, and none of pymoo's shipped decomposition variants
(`Tchebicheff`, `PBI`, `ASF`) normalize by range — every one of them
operates on raw `F` magnitudes after only subtracting the ideal point. Left
unfixed, raw cost (the largest-magnitude objective by roughly an order of
magnitude) would dominate every replacement decision regardless of the
reference-direction weights, effectively collapsing the decomposition to a
cost-only comparison.

`NormalizedTchebycheff` (subclassing pymoo's `Decomposition`) fixes this by
tracking its own running nadir estimate — the component-wise maximum
objective value seen so far, monotonically non-decreasing, mirroring how
`ReferenceDirectionSurvival.norm.nadir_point` behaves for the other two
solvers — and normalizing `F` by `(nadir − ideal)` range before the
standard weighted-Tchebycheff formula. Its `update_nadir()` call is
deliberately a *separate* method from the actual scalarizing computation
(`_do()`), invoked exactly once per replacement step by `ConstrainedMOEAD`
on the union of the neighbourhood's and the offspring's objectives, before
either of that step's two decomposition-value calls — folding the update
into `_do()` itself would let the two calls (`g(x_k)` then `g(y)`) use two
different, inconsistently-informed spans within the same comparison,
biasing every replacement decision toward whichever call happened second.

Chosen specifically as a normalized **Tchebycheff** (not the PBI variant
pymoo's `default_decomp()` would otherwise select for 4 objectives) to
avoid PBI's own extra `theta` penalty hyperparameter — again, no
counterpart on the NSGA-III/QI-NSGA-III side.

## Parameters and references

### Shared with NSGA-III/QI-NSGA-III (reused as-is)

The Das-Dennis reference-direction construction (`N_PARTITIONS=8` → 165
directions for 4 objectives, repurposed here as decomposition weight
vectors), and the SBX/PM operators (`p_cross=0.9`, `eta_cross=20`,
`eta_mut=20`, `p_mut=1/D`) are exactly `Solvers/NSGA3`'s own values — see
[`Solvers/NSGA3/README.md#parameters-and-references`](../NSGA3/README.md#parameters-and-references),
not repeated here.

### MOEA/D-specific

| Parameter | Value | Rationale / reference |
|---|---|---|
| `n_neighbors` (T) | 20 | pymoo's own default — **not tuned** as part of this integration; a candidate for a future ablation |
| `prob_neighbor_mating` | 0.9 | pymoo's own default — probability of drawing mating parents from the neighbourhood `B(i)` rather than the whole population |
| Population size | `len(ref_dirs)` = **165**, not 200 | Structural, not tunable: pymoo's `MOEAD._setup()` sets `self.pop_size = len(self.ref_dirs)` unconditionally — one individual per decomposed subproblem is the algorithm's own definition, unlike NSGA-III/QI-NSGA-III's independently-settable `pop_size`. No Das-Dennis partition count lands on exactly 200 for 4 objectives either (`n_partitions=8` → 165, `n_partitions=9` → 220) — see `docs/superpowers/specs/2026-08-19-moead-integration-design.md` |
| Decomposition | Normalized weighted Tchebycheff | This project's own `NormalizedTchebycheff` — see [above](#why-pymoos-stock-moead-needed-two-subclasses) |
| Constraint handling | Deb (2000) feasibility rule | This project's own `ConstrainedMOEAD` — see [above](#why-pymoos-stock-moead-needed-two-subclasses) |

## Objectives

Identical to `Solvers/NSGA3/` and `Solvers/QINSGA3/` — see
[`Solvers/NSGA3/README.md`](../NSGA3/README.md#objectives). All three
solvers share the same `IRPProblem` (`Solvers/NSGA3/problem.py`), so f1–f4
are computed by exactly the same code for all of them.

## Usage

```bash
python -m Solvers.MOEAD.main                                       # instance_25_clients.json, 1 run
python -m Solvers.MOEAD.main --instance 100 --runs 20               # 100-client instance, 20 seeded runs
python -m Solvers.MOEAD.main --instance 25 --gen 200 --runs 5
```

Or via the local web UI: `python main.py` → select an instance → run
MOEA/D.

To compare against QI-NSGA-III directly (fresh runs, no pre-existing
cache required):

```bash
python -m sensitivity.compare_qinsga3_vs_moead --instance 100
```

To compare all three solvers together (NSGA-III, QI-NSGA-III, MOEA/D) on
one shared instance/seed set/reference front:

```bash
python -m sensitivity.compare_3algos --instance 100
```
